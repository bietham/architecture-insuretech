# Task3 — Проблемы/риски при росте нагрузки и предлагаемое решение

## Контекст (as-is)
- `core-app` и `ins-comp-settlement` получают данные о продуктах через синхронный REST вызов в `ins-product-aggregator`.
- `ins-product-aggregator` в рамках **одного** запроса делает fan-out в страховые компании (сейчас 5, скоро 10), агрегирует и отвечает синхронно.
- Для ускорения есть локальные реплики (кэш/копии) продуктов и тарифов в `core-app` и `ins-comp-settlement`.
- `core-app` обновляет продукты раз в 15 минут; `ins-comp-settlement` — раз в сутки (ночью).
- `ins-comp-settlement` раз в сутки делает REST-запрос в `core-app`, чтобы получить список оформленных за день страховок.

## Проблемы и риски (при росте партнёров и нагрузки)

### 1) Синхронный fan-out = рост латентности и падение стабильности
- Время ответа `ins-product-aggregator` становится функцией **самого медленного** партнёра + сетевых задержек.
- При росте числа страховых компаний (5 → 10) вероятность таймаута/ошибки резко растёт.
- Риск каскадных отказов: деградация партнёра → рост очередей запросов → рост потребления памяти/пулов → рестарты.

### 2) Отсутствие backpressure и контроля нагрузки на интеграции
- REST-агрегация “в момент запроса” не даёт нормально дозировать обращения к партнёрам.
- При пиковых периодах (или при ретраях) можно превысить лимиты партнёров и усугубить ошибки.

### 3) “Расписание” запросов создаёт пиковые всплески
- `core-app` каждые 15 минут может создавать “ступеньку” нагрузки на `ins-product-aggregator`.
- Ночной запуск `ins-comp-settlement` даёт крупный батч запросов (и к `ins-product-aggregator`, и к `core-app`) → риск ночных инцидентов.

### 4) Дублирование данных о продуктах без гарантированной согласованности
- Локальные реплики в `core-app` и `ins-comp-settlement` обновляются с разной частотой → расхождения.
- Нет формальной модели версионирования/валидности (какая версия каталога сейчас актуальна?).

### 5) REST “ins-comp-settlement → core-app” для дневных продаж — tight coupling
- Ночной отчёт зависит от доступности `core-app` и сети.
- Большой ответ (все оформленные за день) → риск таймаутов, OOM, повторов, сложной идемпотентности.

### 6) Непрозрачность интеграций и сложность диагностики
- Ошибки партнёров проявляются как “иногда таймаут/500” на стороне внутренних сервисов.
- Без явного слоя асинхронности сложнее отделять “данные временно недоступны” от “сервис умер”.

### 7) Рост стоимости и технического долга
- Чем больше партнёров — тем сложнее удерживать SLA на синхронной агрегации.
- Ретраи и таймауты превращают проблему в “плавающую” и трудно воспроизводимую.

## Целевое решение (to-be)

### Ключевая идея
Перевести обмен **каталогом продуктов** и **фактами оформленных страховок** на **Event Streaming**, оставив REST только там, где нужен request/response (например, пользовательский поиск/оформление внутри core-app).

### 1) Event Streaming для каталога продуктов и тарифов
- `ins-product-aggregator` перестаёт агрегировать “на лету” для внутренних потребителей.
- Вместо этого:
  1) периодически (или по расписанию) забирает данные у страховых компаний **асинхронно** и дозировано;
  2) нормализует/агрегирует в “канонический каталог”;
  3) публикует событие `ProductCatalogUpdated` (или батч событий `ProductUpserted`) в топик `product-catalog`.

- `core-app` и `ins-comp-settlement` подписываются на `product-catalog` и обновляют свои локальные read-модели/реплики.
- Для согласованности вводим:
  - версию/epoch каталога (`catalogVersion`, `effectiveFrom`, `sourceTimestamp`);
  - идемпотентную обработку по ключу `(providerId, productId, version)`.

### 2) Event Streaming вместо ночного REST “ins-comp-settlement → core-app”
- `core-app` при оформлении страховки публикует доменное событие:
  - `PolicyIssued` / `PolicyCreated` / `PolicyPaid` (в зависимости от домена).
- `ins-comp-settlement` потребляет эти события и ведёт собственную read-модель “Оформленные за период”.
- Ночной расчёт становится локальной операцией над своей БД; REST-запрос к `core-app` не нужен.

### 3) Transactional Outbox — ДА
Чтобы события не терялись и не дублировались “случайно”, используем **Transactional Outbox**:
- В `core-app`: запись полиса в БД и запись события в outbox — **в одной транзакции**.
- Отдельный publisher (sidecar/worker) читает outbox и публикует в брокер.
- Аналогично можно сделать в `ins-product-aggregator` для `ProductCatalogUpdated`.

### 4) Технические детали (коротко)
- Брокер: Kafka (или managed Event Streaming).
- Схемы: Schema Registry (Avro/Protobuf/JSON Schema), обязательная совместимость.
- Consumer group’ы, ретраи, DLQ (dead-letter topic) для “ядовитых” сообщений.
- Idempotency: обработчики должны быть идемпотентны (dedup по eventId).
- Наблюдаемость: лаги консьюмеров, DLQ, метрики публикации, трассировка.

## Что остаётся на REST
- Внешние B2B/B2C API (через API Gateway), пользовательские операции.
- Внутренний REST `core-app → client-info` (если это транзакционный запрос “получить/обновить данные клиента”).
- REST `core-app → ins-product-aggregator` может остаться только для “on-demand” запросов, если бизнес требует актуальности “прямо сейчас”, но основа — поток.
